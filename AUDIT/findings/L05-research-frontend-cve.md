## Findings

### [P2] Overly permissive Content-Security-Policy enables inline script execution via `'unsafe-inline'`
- **Where:** `src/Frontend/YO4X.Web/index.html:6-9`
- **Confidence:** CONFIRMED
- **Code:**
  ```html
      <meta
        http-equiv="Content-Security-Policy"
        content="default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data:; connect-src 'self' https://127.0.0.1:7210 ws://127.0.0.1:4173; worker-src 'self' blob:; object-src 'none';"
      />
  ```
- **Failure:** When an attacker manages to inject script content through any future DOM XSS vector or third-party payload, the browser executes the injected script unconstrained because `script-src` includes `'unsafe-inline'`. Because React 19 entry points use ES modules (`<script type="module" src="/src/main.tsx">`), allowing unrestricted inline script execution defeats the primary cross-site scripting mitigation provided by CSP.
- **Fix:** Remove `'unsafe-inline'` from `script-src` in `index.html`. If inline bootstrapper scripts are ever needed, supply cryptographic hashes (`'sha256-...'`) or nonces (`'nonce-...'`) instead of allowing all inline scripts.

### [P2] Vite development proxy explicitly disables TLS certificate validation
- **Where:** `src/Frontend/YO4X.Web/vite.config.ts:10-21`
- **Confidence:** CONFIRMED
- **Code:**
  ```typescript
      proxy: {
        '/v1': {
          target: 'https://127.0.0.1:7209',
          changeOrigin: false,
          secure: false,
        },
        '/health': {
          target: 'https://127.0.0.1:7209',
          changeOrigin: false,
          secure: false,
        },
      },
  ```
- **Failure:** When developers or automated environments proxy API calls through the Vite dev server to backend control plane endpoints (`/v1`, `/health`), `secure: false` instructs the proxy to ignore all TLS certificate errors and mismatches. If run in a shared developer network or behind a rogue local interceptor, upstream API traffic—including bearer access tokens generated by `oidc-client-ts`—can be intercepted via MITM without raising certificate alerts.
- **Fix:** Remove `secure: false` (or set `secure: true`) in `vite.config.ts` and ensure the local development certificate authority is trusted by Node's certificate store.

### [P2] Content-Security-Policy meta tag hardcodes loopback authority port 7210 and omits backend API port 7209
- **Where:** `src/Frontend/YO4X.Web/index.html:8`
- **Confidence:** CONFIRMED
- **Code:**
  ```html
        content="default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data:; connect-src 'self' https://127.0.0.1:7210 ws://127.0.0.1:4173; worker-src 'self' blob:; object-src 'none';"
  ```
- **Failure:** When the web app makes direct API requests to the backend control plane on `https://127.0.0.1:7209` (as configured in `vite.config.ts`) instead of using relative paths, or when deployed to a staging/production origin, the browser's CSP blocks all HTTP/WebSocket API calls because `connect-src` only allows `'self'`, `https://127.0.0.1:7210`, and `ws://127.0.0.1:4173`. Furthermore, delivering CSP via a static `<meta>` tag prevents dynamic environment adaptation and cannot enforce server-level framing constraints (`frame-ancestors`).
- **Fix:** Remove static loopback hostnames and ports from the HTML `<meta>` tag, configure `connect-src 'self'` for proxied setups, and emit dynamic Content-Security-Policy headers from the reverse proxy/web server.
