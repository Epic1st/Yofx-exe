# F08 — Assembly Identity and Codegen Runtime Contract

## Scope audited
- `src/Runtime/YO4X.Mql5.CodeGen/Mql5AssemblyBuilder.cs` (110 lines)
- `src/Runtime/YO4X.Mql5.CodeGen/Mql5RuntimeContract.cs` (89 lines)

## Verdict
The codegen/runtime contract boundary and compilation contract definitions are clean, deterministic, and enforce strict compile-time decoupling from Roslyn and the concrete runtime implementation. However, `Mql5AssemblyBuilder.Build` silently drops diagnostics produced during semantic binding and omits validation on the supplied `assemblyName`, causing unhandled exceptions when invalid names are provided. Furthermore, `Mql5AssemblyBuilder` is currently bypassed by live and backtest execution runners.

## Findings

### [P2] Mql5AssemblyBuilder.Build silently drops semantic binder diagnostics
- **Where:** `src/Runtime/YO4X.Mql5.CodeGen/Mql5AssemblyBuilder.cs:87-90`
- **Confidence:** CONFIRMED
- **Code:**
  ```csharp
          foreach (Mql5IrV2Module module in modules)
          {
              Mql5BindResult bound = Mql5Binder.Bind(module);
              Mql5CodeGenResult result = Mql5CodeGenerator.Generate(module, bound.Model);
              diagnostics.AddRange(result.Diagnostics);
  ```
- **Failure:** When `Mql5Binder.Bind` produces informational, warning, or error diagnostics (such as `Mql5BindDiagnosticCodes.BudgetExhausted`, `Mql5BindDiagnosticCodes.UnsupportedBuiltin`, or unresolved member diagnostics), `bound.Diagnostics` is ignored. `diagnostics.AddRange` only consumes `result.Diagnostics`. Any diagnostic emitted by the binder that is not independently regenerated by `Mql5CodeGenerator` is silently lost from the returned `Mql5CompilationResult.Diagnostics`.
- **Fix:** Add `diagnostics.AddRange(bound.Diagnostics);` immediately after invoking `Mql5Binder.Bind(module)`.

### [P2] Mql5AssemblyBuilder.Build does not validate assemblyName before generation
- **Where:** `src/Runtime/YO4X.Mql5.CodeGen/Mql5AssemblyBuilder.cs:64-79`
- **Confidence:** CONFIRMED
- **Code:**
  ```csharp
      public static Mql5CompilationResult Build(
          string assemblyName,
          IReadOnlyList<Mql5IrV2Module> modules,
          IMql5CompilationHost host)
      {
          if (host is null)
          {
              return Mql5CompilationResult.Failed(
                  Mql5CodeGenDiagnosticCodes.InternalFailure, "No compilation host was supplied.", 1, 1);
          }

          if (modules is null || modules.Count == 0)
          {
              return Mql5CompilationResult.Failed(
                  Mql5CodeGenDiagnosticCodes.InternalFailure, "No modules were supplied.", 1, 1);
          }
  ```
- **Failure:** Supplying a `null`, empty, or whitespace `assemblyName` passes initial checks, executes full binding and C# code generation across all modules, and then causes implementations like `RoslynMql5CompilationHost` to throw an unhandled `ArgumentException` at line 51 of `RoslynMql5CompilationHost.cs` instead of returning a structured failure `Mql5CompilationResult`.
- **Fix:** Add a validation check for `string.IsNullOrWhiteSpace(assemblyName)` at the start of `Build` that returns `Mql5CompilationResult.Failed(Mql5CodeGenDiagnosticCodes.InternalFailure, "No assembly name was supplied.", 1, 1);`.

### [P3] AssemblyInfo.cs contains misleading comment regarding project reference topology
- **Where:** `src/Runtime/YO4X.Mql5.CodeGen/AssemblyInfo.cs:3-7`
- **Confidence:** CONFIRMED
- **Code:**
  ```csharp
  // The emitter's name and type mappings are internal because they are an implementation detail of
  // translation, not a public contract. They still have to be held against the runtime interface
  // they emit calls into, and that comparison can only be made from an assembly that references
  // both — which is this one.
  [assembly: InternalsVisibleTo("YO4X.Mql5.Runtime.Tests")]
  ```
- **Failure:** The comment states that `YO4X.Mql5.CodeGen` ("which is this one") references both the emitter and the runtime interface. In reality, `YO4X.Mql5.CodeGen` deliberately avoids referencing `YO4X.Mql5.Runtime` (using local stub definitions in `Mql5RuntimeContract.cs`), and `YO4X.Mql5.Runtime.Tests` is the assembly referencing both.
- **Fix:** Update the comment in `AssemblyInfo.cs` to accurately state that `YO4X.Mql5.Runtime.Tests` is the referencing assembly comparing the internal tables against the runtime surface.
