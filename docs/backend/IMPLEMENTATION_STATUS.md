# Backend implementation status

## Active scope

The repository implements the buildable U0/A0-A3 safety foundation. Broader target architecture remains staged and is not silently represented as complete. In particular, production broker-command authorization is hard-disabled, GatewayHost is proof-only, and no supplied strategy has semantic, compile, parity, or runtime proof.

## Implemented foundation

- .NET 10 solution and module dependency boundaries.
- Strict API problem/correlation/idempotency/concurrency primitives.
- User and admin session domain foundations.
- Credential-ingestion grants and a write-only secret-material boundary.
- Exact-role credential reservation, release, completion, rotation, expiry, and recovery capabilities. Secret-ingestion and worker roles have execute-only capabilities and no raw broker-account or credential-grant mutation authority.
- Deployment, gateway, strategy, incident, support, and privacy domain foundations.
- Policy-vector, command, approval, runtime, tenancy, audit, outbox, and PostgreSQL workstreams with dedicated tests.
- Independent executable boundaries and health contracts.
- Anonymous startup/readiness endpoints use one fixed-key, process-local single-flight snapshot. Concurrent callers share one dependency probe, caller cancellation cannot cancel the shared probe, the probe has an independent five-second deadline, and a completed result is reused for at most one second. This bounds database/catalog amplification and makes the maximum stale-readiness window explicit; it is not a substitute for edge rate limiting.
- PostgreSQL adapters for user control-plane and admin workflows, with transactional idempotency, audit, and outbox boundaries.
- PostgreSQL-owned authority clocks for control, admin, runtime-control, idempotency, worker claims, freshness, lifecycle transitions, and their audit/outbox evidence. Injected application clocks are not trusted as an authority source.
- Durable PostgreSQL-owned scan cursors make outbox, credential-expiry, deployment-projection, and user-operation tenant traversal fair across restarts and concurrent worker instances. Per-tenant deployment traversal is durable as well. The worker can write only the exact next cursor UUID; database triggers own timestamps, rotation counters, and row versions, while readiness fails when a full rotation exceeds the configured SLA. Cursor health is liveness evidence, not proof that a compromised worker completed the associated business work.
- User-operation dispatch is globally ordered across dispatch and reconciliation work, prioritizes protective account/deployment operations, uses database-owned bounded deferral, and never expires a protective operation or terminalizes an already handed-off operation merely because local acknowledgement is missing. Broker and deployment results enter through exact-role, execute-only PostgreSQL capabilities bound to the immutable v2 dispatch and a canonical one-use 256-bit result token; raw result-table insertion is denied.
- The database and C# scaffolding for the requested-v4/result-v5 invocation boundary is implemented in an additive migration, strict role-specific adapters, and the production `PostgresUserOperationWorkStore`: generation-bound supervisor delivery, one-shot gateway begin, post-commit credential authorization, exactly one provider call, typed target observation, ambiguity, expiry, reconciliation challenges, exact result replay, and atomic broker/deployment projection. Reconciliation enforces the fixed worker actor and exact operation correlation before any evidence branch; wrong correlation returns no row and takes neither the U0 authority lock nor an operation row lock. Fresh PG18 facts exercise the SQL state machine and adapters with a deterministic non-broker test provider. This is not an authenticated production transport or broker proof. Runtime evidence can execute only result-v5 and has no raw invocation, target, audit, or outbox table privileges.
- MFA-gated, one-time strategy-source import with digest-only capability persistence, immutable raw-source/static-evidence storage, database-derived authority, and no strategy-promotion rights.
- Deterministic signed numeric risk-policy evaluation as a pure domain slice. Its output is not accepted as production dispatch authority.
- Fail-closed isolated MQL5 compile orchestration with signed attestation validation; no local compiler or terminal execution.
- A durable broker-command schema and coordinator proof boundary: immutable authorization/command/evidence content, frozen signed execution-lease bytes, claim/recovery/reconciliation state transitions, audit evidence, database time, and least-privilege role separation.
- `yo4x_gateway_runtime` has execute-only access to the exact lifecycle functions and no raw authority/evidence table privileges. It cannot call `control.authorize_broker_command`; `yo4x_trade_authorizer` cannot call that function either while the trusted risk authority is absent.
- GatewayHost owns one gateway-runtime database connection, does not register the raw PostgreSQL store for resolution, exposes no order endpoint, seals coordinator submission off, and remains not-ready for mutation use.
- GatewayHost references an authenticated one-request process transport rather than the MT5 adapter. Its local-fixed-volume SHA-pinned launch manifest, strict bounded frames, single pre-verification deadline budget, and sanitized failure surface provide a same-host fail-closed boundary. Synchronous filesystem operations and `Process.Start` are not preemptible, and a forced cleanup is only a best-effort tree-kill request plus bounded root-handle wait whose outcome remains unconfirmed. The child currently registers only a proof executor that makes no vendor call.
- Supervisor and GatewayHost keep `UserOperationProtocol.Enabled` false by default and expose only role-local unavailable protocol ports. Enabling it before the authenticated cross-host transport exists fails startup with a sanitized capability error; neither host wires a credential boundary, provider invoker, cross-role PostgreSQL adapter, in-process shortcut, or broker call.
- Reference-driven read-only operational frontend with typed API contracts and production fail-closed data loading.
- Architecture tests that pin the supplied vendor hash and enforce dependency/output isolation.

## Durable broker-command safety posture

- `PostgresBrokerCommandStore.AuthorizeAsync` fails with `BROKER_COMMAND_RISK_AUTHORITY_UNAVAILABLE`. A caller-provided `RiskInput` or `NumericRiskDecision` is not trusted as authority.
- A dispatch claim returns database `AuthorityNowUtc`; the coordinator advances it only with monotonic elapsed time. Before any possible gateway entry it refreshes all bindings, signature/trust, demo-only, provenance, freshness, claim, lease, authorization, and minimum-window checks.
- PostgreSQL accepts a new submission result only while database authority remains before the dispatch-claim expiry. An exact replay is accepted only when the originally persisted `send_completed_at` was also within that claim; after expiry, a caller cannot add a new `Accepted` or `Unknown` result and recovery exclusively owns the transition to durable `Unknown`.
- `SubmissionEnabled` is false by default and GatewayHost does not expose a configuration switch that can turn it on. The present host therefore records a pre-entry `submission_disabled` result with `PreInvocationNotSentProven = true`, no broker identifiers, and no gateway invocation.
- Once the gateway method is entered, the not-sent proof is always false. Only `Accepted` or `Unknown` can cross the persistence boundary and both require reconciliation; post-entry `Rejected` or `SubmissionDisabled` is normalized to `Unknown`.
- The application validator performs a narrow structural-correlation check for `Place`: a persisted non-null broker order identifier must exactly match the reported order and complete atomic snapshot. Even an exact match remains `Inconclusive` because the gateway observation is not authenticated broker authority. `ModifyProtection`, `Cancel`, and `Close` are also always inconclusive. Production SQL independently accepts no conclusive terminal match, so durable reconciliation remains `Unknown`.
- The original gateway artifact digest/evidence/state is revalidated when reconciliation begins and again when it completes. Revocation or evidence loss prevents completion.
- Dispatch and reconciliation rehydrate the exact signed execution-lease envelope frozen on the command. A later lease-row renewal cannot silently substitute different signed bytes.
- Timeout, cancellation, exception, late completion, lost persistence acknowledgement, expired claim, and missed reconciliation deadlines fail toward durable `Unknown`; no ambiguous mutation returns to `authorized` for blind retry.

See [`DURABLE_BROKER_COMMAND_PIPELINE.md`](./DURABLE_BROKER_COMMAND_PIPELINE.md) for the complete boundary and limitations.

## Intentionally disabled or deferred

- Live trading, raw order endpoints, and any production broker mutation.
- Public signup and general user onboarding.
- Local runtime mode.
- General semantic MQ5 conversion, private-source viewing, and any compile/runtime claim without isolated attestation.
- Billing and broad privacy automation.
- Production provider integrations until providers and policies are selected.
- A production outbox destination/router and authenticated runtime consumer. The worker intentionally falls back to an unavailable destination, so no user-operation v3 or requested-v4 dispatch is represented as delivered to an executor.

## Hard blockers before demo MT5 execution

- The remote Git history still contains the now-deleted vendor `Examples.cs` with numerous literal MT5 login/password/server tuples, including an explicitly live-labelled example, plus proxy credential material. Every affected MT5/proxy credential must be treated as compromised and revoked or rotated; the deletion must be landed and remote refs, caches, and forks scrubbed through a coordinated credential-incident procedure. The current tree and generated evidence contain none of those values.
- The remote Git history also retains a historical Telegram bot token in the initial supplied MQL corpus commit. It must be revoked or rotated and removed through the same coordinated history-remediation process. Current MQL source and generated artifacts contain no matching token value, and the redundant tracked aggregate source archive that retained the pre-redaction copy has been removed from the current tree and explicitly ignored.
- No trusted isolated Windows runner and no approved platform snapshot/signing key are configured on this machine.
- Written commercial/provenance approval for the exact unsigned vendor DLL is not present.
- A production write-only secret provider and signed receipt-verification implementation have not been selected or configured. The local DPAPI maintenance vault is deliberately disconnected from GatewayHost.
- Production broker-command authorization is unavailable until a trusted component authenticates a signed gateway snapshot, derives broker-dependent risk input deterministically, binds authoritative risk-day/order-rate/exposure state, verifies the signed policy, and runs the numeric evaluator over those exact immutable facts.
- Normalized trade `BrokerCommand` reconciliation lacks authenticated broker-observation provenance. Its production SQL therefore cannot accept a terminal trading result; this is separate from capability-bound broker-account user-operation evidence.
- No production component currently transports requested-v4 mutation messages across the authenticated Supervisor/Gateway/credential boundaries. A dedicated same-host connection-only credential child exists and is tested, but the authenticated outbox consumer and destination, mutation provider/observer, production secret provider, hardened isolation, and restart coordinator remain absent. The hosts therefore keep mutation protocol submission disabled.
- The initial v2 mutation envelope does not carry its database-owned result-capability expiry, assignment-lease deadline, or a bounded execution deadline. The generic outbox may first deliver an arbitrarily old row, so an execution-enabled receiver must not consume v2. A successor contract and execute-only database invocation claim must revalidate the exact current fence, active assignment, lease, policy/resource binding, and proof margin with `clock_timestamp()`, then durably record `send_in_progress` before IPC. Any post-start ambiguity remains reconciliation-only; a stale message must never reach the gateway.
- The original one-use result capability expires after 24 hours. Exact accepted-result replay remains valid. Database/C# reconciliation-challenge issuance, consumption, canonical result handling, and production work-store scheduling are implemented as fail-closed scaffolding so a current assignment can observe state without republishing or re-executing the original mutation. An authenticated transport, consumer, provider/observer, and restart path have not exercised that flow against a real broker, so an ambiguous operation can still remain `unknown` and readiness stays unhealthy.
- The implemented child-process transport is a same-host fail-closed mechanism with bounded protocol sizes, not a hard wall-clock bound, sandbox, privilege boundary, Windows job-object, network policy, container, or VM. Synchronous launch/filesystem stalls and descendant containment remain unproved. A mutation-capable adapter still requires an approved isolated runner/image, constrained egress, immutable deployment authority, and externally attested containment/restart behavior.
- Strategy-specific semantic mappings, complete dependency snapshots, isolated compiler attestations, reference parity, account-mode assumptions, and safe order behavior have not been proven for any supplied file.

The demo credential source is never copied into source, configuration, logs, test output, reports, or browser code. The dedicated connection-only worker loaded the exact pinned DLL and proved one Vantage demo login plus confirmed disconnect. The mutation adapter remains `SubmissionDisabled`; this status claims no order, modification, strategy execution, or terminal broker reconciliation.
